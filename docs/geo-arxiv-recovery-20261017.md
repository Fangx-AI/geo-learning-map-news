## 官方依据与问题定位

arXiv 的 OAI-PMH、RSS 和查询 API 共同遵循请求至少间隔 3 秒、同时只进行一个请求的限制；该限制适用于使用者控制的所有机器。[官方 API 使用条款](https://info.arxiv.org/help/api/tou.html)

查询 API 按每日论文发布周期更新，官方手册建议同一查询一天请求一次并缓存。`published` 表示首次版本日期，`updated` 表示所取版本的更新日期；带版本号的论文 ID 与不带版本号的链接含义不同。[API 使用手册](https://info.arxiv.org/help/api/user-manual.html)

RSS 是按学科提供的每日发布列表，支持多个学科合并请求，最多返回 2,000 条；它提供的近期分类列表与跨时间的关键词查询不是同一种覆盖范围。[官方 RSS 说明](https://info.arxiv.org/help/rss.html)

改动前的本地代码存在两个确定问题：

- 三个来源虽然配置了 `interval_minutes: 360`，公开采集循环却每轮读取全部启用来源；持续循环约每 30 分钟运行，来源间隔没有生效。
- 网络层没有跨 `arxiv.org`、`export.arxiv.org`、`rss.arxiv.org` 的公共节流；不同 worker 可以同时发请求。列表读取对暂时性 500 / 502 / 503 / 504 的一次重试只等待 1 秒。429 原本就不自动重试，本轮保留这一行为。

## 实施方案

来源调度按保存的最近尝试时间和 `interval_minutes` 判断是否到期。两路相同查询 API 调整为 1,440 分钟，`cs.IR` RSS 保持 360 分钟并复用条件缓存。单源失败不隐藏历史条目，也不以停用来源消除错误。按连续运行的理论上限，三路定时列表请求从约 144 次 / 日降为 6 次 / 日；不含暂时故障重试、图片或手动运行。

`packages/backend/src/lib/arxiv-throttle.ts` 给全部 `arxiv.org` 及其子域共用一个进程内队列。`guardedFetch` 在每个实际网络跳转前进入队列，完整消费或取消响应体后释放：

- 同时最多一个正在读取的 arXiv 响应，请求开始时间至少相隔 3 秒，使用单调时钟。
- 重定向和列表的暂时故障重试也经过相同队列，不另开不受限的路径。
- DNS、SSRF、跨域敏感请求保护仍按原有规则执行；排队和间隔等待计入原请求超时。
- 等待被取消后不会继续发请求，不会让后面的请求越过仍在读取的响应；正文读取失败也释放队列。
- 其他域名不延迟；`arxiv.org.example.invalid` 不会误匹配。429 / 403 不新增立即重试。

队列是单个 Node 进程内的限制。本站公开采集的数据库周期锁保证正常守护不会重复并行运行；如果未来让其他独立进程或机器也采集 arXiv，应集中入口或增加共享限速，不能把该队列误称为跨机器保证。

## 替代入口评估

已运行的 `cs.IR` RSS 是当前可核实的独立发布入口，继续在本地筛选 GEO、AI 搜索、引用和测量相关标题与摘要。它在 08:33 的正常周期实际读到 26 条、留下 8 条，足以证明此入口当时可用，但不能证明它覆盖全部引用研究。

进一步扩大 RSS 可考虑官方支持的多学科合并订阅，再本地按论文 ID / 版本和相关性筛选；本轮没有启用或实测新的合并地址。单凭 `cs.IR` 分类不能证明覆盖 `cs.CL`、`cs.AI` 或其他学科的引用论文，短期 RSS 窗口也不能替代历史检索。因此不删除或改写现有两路查询，更不在 API 限流后自动换查询别名或批量抓分类 HTML。

也暂不合并两路 API 查询：二者各自取最近 30 条，直接合并后仍只取 30 条会减少一类研究的覆盖；增加分页又可能抵消节省的请求。先按每日缓存和共享节流稳定运行，再凭持续数据决定是否有合并价值。

原始论文链接、已有版本号、日期和来源身份保持不变。API 的首次发布日期不会被更新日期冒充；RSS 和 API 读到的无版本 / 有版本论文也不在本轮强行合并。只保存与展示摘要和原文链接，不复制论文全文。
