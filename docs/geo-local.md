# 本机启动与恢复

完成 README 的 Node 依赖、`.env` 和本机 PostgreSQL 初始化后，在项目目录执行：

```powershell
./scripts/start-geo.ps1
```

它先核验数据库、API、网页和公开采集守护，复用已经可用的服务，按依赖顺序补启动缺失项。启动的子进程在后台运行，关闭这条命令的终端不影响它们。没有安装 Windows 开机任务；电脑重启后重新执行即可。数据库仍只使用 `127.0.0.1:55432` 和已有的 `.data/postgres`，缺少运行库或初始化目录时会报错，不覆盖数据。

只查看状态，不启动或修改服务：

```powershell
./scripts/start-geo.ps1 -Action status
```

也可直接运行 Node 入口：

```powershell
node --env-file=.env scripts/geo-local.ts start
node --env-file=.env scripts/geo-local.ts status
```

API 和网页通过数据库健康、本站 OpenAPI 标识、公开采集状态结构核验；网页还核验本站 HTML。端口被其他程序占用或身份检查失败时，命令停在可解释的错误，不结束占用进程。守护进程用操作系统进程锁防止重复父进程，实际采集继续使用 PostgreSQL 互斥锁；持锁连接丢失会结束该轮，守护入口等待 5 分钟再试。状态中的“守护入口已运行，等待自动重试”表示父进程存在，不能据此推断最近一轮成功。

当 API 或采集守护缺失时，恢复前先执行迁移。网页缺少构建产物时自动构建；已有产物默认复用。需要显式重建时，先停止网页服务，再运行：

```powershell
./scripts/start-geo.ps1 -Rebuild
```

只要网页端口正在使用，重建就会被拒绝，避免运行中的旧 SSR 引用被替换的新 assets。此入口不提供自动停止、覆盖现有服务或回滚数据库的命令。若中途失败，已经恢复的服务会保留；检查错误后再次执行 `start` 即可。

公开采集仅在 `.env` 的 `PUBLIC_FEED_COLLECT_ENABLED=true` 时补启动。启动器给新子进程关闭原引擎采集、模型调用、飞书推送和 IndexNow；不会修改 `.env`。已有进程保持其原有设置。

开启 `PUBLIC_TRANSLATION_ENABLED=true` 后，公开采集守护同时维护独立中文翻译队列。默认 `PUBLIC_TRANSLATION_PROVIDER=bing`，无需安装模型或填写 API 密钥；原文、译文和服务冷却状态保存在数据库，重启后继续。也可安装 `.data/translation/` 中的多语言模型并设为 `local`，离线处理。改变开关或通道后需重启采集守护。翻译失败时保留原文，不中断资讯采集。安装与验证见 [翻译配置](geo-translations.md)。

后台日志与启动记录位于 `.data/local-services/`，其中 `launches.jsonl` 记录本入口创建的服务、PID、时间与日志路径。这些是本机私有诊断文件，不应发布或提交。PID 仅供核查，不能在未确认对应进程身份的情况下据此结束进程。

若数据库返回 `57P03`，状态会说明数据库正在启动恢复。保留现有进程等待，不要反复启动、删除数据目录或关闭持久化设置。数据库入口现已保留经过连接密码脱敏的 PostgreSQL 启动日志；这仅影响之后启动的进程，已运行进程不会被重启。

2026-10-16 验证：6 项独立测试覆盖复用、组件启动顺序、端口冲突、服务身份、重复守护和锁释放。实机暖启动前后数据库/API/网页 PID 一致，没有新增启动记录；网页运行时 `--rebuild` 被拒绝。已有服务运行中，未通过停机实验验证整机冷启动；缺失组件流程由本地测试验证。

随后升级时已用该入口真实恢复缺失的采集守护与 API，两次均复用原数据库和运行中的网页。恢复后的采集轮次正常完成，API 完整分页通过；启动记录在 `.data/local-services/launches.jsonl`。这不等于验证了电脑关机后的自动启动。

## 采集守护重启时的计划

守护启动时保留数据库中尚未到期的 `waiting` / `retrying` 下轮时间，避免更新程序或恢复进程时立即再抓一次。正常停止等待中的守护会原子保留原到期时间，带有效计划的 `stopped` 重启也会继续等待；重复停止不会延后计划。等待期间心跳与中文翻译继续运行。首次运行、已到期、无计划的停止状态或上一轮运行中断的任务正常开始；显式不带 `--watch` 的单次采集仍立即执行。这个等待不会清除来源失败记录，也不会把 403/429 记为采集成功。

此路径通过 2 项独立测试与 3 项隔离数据库测试，覆盖首次运行、等待／重试后正常停止、重复停止、运行中退出及过期计划。本轮没有停止正在运行的生产采集器做重启实验；新启动逻辑会在下一次正常启动时加载。

2026-10-17 08:50 更新已实际加载该逻辑：新守护日志显示保留原计划、等待约 14 分钟，同时继续中文翻译；数据库的下一轮仍为 09:03:40，没有因更新立即再抓所有来源。正常信号退出的计划保留由隔离数据库测试验证，本次 Windows 服务更新不冒充该信号路径测试。

普通来源的间隔也已生效：`--watch` 在读取列表前对照持久化 `last_attempt_at` 和来源 `interval_minutes`。尚未到期返回本轮 `skipped`，不改存储的状态、成功时间或错误；失败也遵循间隔。单次维护命令仍可明确读取已核实的新入口。arXiv API 两路为 1,440 分钟，分类 RSS 为 360 分钟。详见 [arXiv 恢复与请求约束](geo-arxiv-recovery-20261017.md)。
